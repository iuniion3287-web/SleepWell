### 1-3. Sleep-EDF 1분 → 30초 역집계 규칙 ★아직 미결 (가장 중요)

소빈 #2는 Sleep-EDF 30초 epoch 정답으로 confusion matrix / F1 / kappa 를 뽑는 파이프라인이다.
1분 모델을 거기에 붙이려면 각 30초 정답 epoch 를 대응하는 1분 값으로 되돌리는 규칙이 필요하다
(1분 안에 정답 stage 가 두 개면 다수결 등).

여기서 위험한 게 있다. `EpochAggregator` 주석에 이미 기록돼 있다:

> 평가코드는 `(subject_id, night, epoch_idx)` 로 inner join 한다. 이 값들이 **행 번호가 아니라
> 시각 좌표**여야 하는데, 단위만 30초 → 1분으로 어긋나면 **에러 없이 조용히 틀어진다.**
> (실측: night 어긋나면 F1(macro) −0.210 / Kappa −0.222, 오류 메시지 0줄)

같은 실수가 `epoch_idx` 단위 차이로 반복될 수 있다. **역집계 규칙을 정하기 전에는
1분 성능 수치를 발표자료(#9)에 올리면 안 된다.**

### 1-4. `SAMSUNG_TIMES_ARE_UTC = true` 확정 (혜지 확인 필요, 소빈 경유)

삼성헬스 CSV 의 `start_time` 이 UTC 라는 건 **소빈의 가설**이다. 근거는
"5시간 이상 수면이 원본 기준 18~21시 시작 → UTC 로 읽어야 KST 03~06시 취침으로 자연스럽다" +
삼성헬스 export 문서 인용.

플래그로 분리돼 있어서(`CsvFileSource` 의 `SAMSUNG_TIMES_ARE_UTC`) 뒤집는 건 상수 한 줄이다.
영향: `Process S` 는 무관, **`C_sleep`·`phaseRef` 는 9시간 밀린다.**

**확정 전까지 C 계열 절대 수치를 보고서에 쓰면 안 된다.** 이 값을 명시하고 써야 한다.

## 2. 서윤 언니한테 (모델 쪽)

### 2-1. Hybrid 모델 확정 시점 — 임시 Two-Process 교체 시점

`SleepAnalysisPipeline` 의 `recommendation` 은 여전히 `null` ("준비 중")이다.
Hybrid 모델이 나오면 `recommendation` 과 `futureS` 를 교체한다.
1분 버전으로 정리했으니, 교체 시 epoch 인자만 맞춰 넘기면 된다.

### 2-2. C_sleep 의 phaseRef 가 epoch 간격에 예민하다

검증에서 30초 → 1분으로 바꾸니 `phaseRef` 가 조금 어긋나 C_sleep 가 0.0018 만큼 달랐다(진폭 0.15 대비 1.2%).
Hybrid 모델에서 C 나 리듬 위상을 결과값으로 쓴다면 **epoch 간격을 고정하고 그 기준으로 보고서를 쓰는 게 맞다.**
안 정하면 "같은 사람이 시간대만 바꿨는데 리듬 위상이 달라진다"가 생긴다.

### 2-3. epoch 간격을 모델 입력이 아니라 결과 해상도로 볼지

이번 1분 전환은 **입력 격자**만 바꿨다. 만약 의도가 "그래프를 덜 촘촘하게"였다면,
`scHistory` 전달 필터(10~15분)로도 되므로 epoch 를 안 바꿔도 된다.
목적이 무엇이었는지 확인해야 불필요한 변경이 안 남는다.

### 회귀 테스트 — 왜 이게 필요했는가

`clockHours()` 버그가 테스트 없이 통과했던 게 이번 학기 제일 큰 문제였다.
회귀 비교는 "30초 vs 1분" 만 봤고 두 버전이 같은 버그를 공유해서 차이가 안 났다.
정작 봐야 할 건 **"시간이 흐르는데 값이 안 움직이는가"** 인데 그런 테스트가 없었다.

그래서 `clockHours` 를 private 에서 visibility 올려 직접 테스트하지 않고,
**공개 API(`compute`)로 행동을 보는** 테스트를 만들었다. 리팩터링에도 안전하다.

### 테스트가 실제로 버그를 잡는지 확인했다

회귀 테스트는 "통과"만증명하지 않으면 쓸모없는 다. 그래서 버그를 되돌린 복사본을 만들어
같은 스위트를 돌렸다. → **6개가 FAIL** (C 가 시 단위로 뭉개짐, phaseRef 가 정수로 붙음 등).
개수를 붙인 게 아니라 "어떤 테스트가 잡는지"까지 봤다.

### 테스트를 쓰면서 발견한 내 하네스의 버그 2개

1. **`main()` 이 Unit 을 돌려줘서 JVM 종료 코드가 항상 0이었다.**
   → `RESULT=FAIL` 이 출력돼도 스크립트 요약은 "전체 통과" 로 집계됐다.
   CI 에 물으면 조용히 통과하는, 가장 나쁜 종류의 오류. `exitProcess(code)` 로 고침.
2. **폴더가 없으면 조용히 건너뛰면서 통과로 집계됐다.**
   → 경로 오타로 아무것도 안 돌았는데 "전체 통과" 가 나오는 경우. `SKIP` 을 별도 상태로 분리하고,
   **아무 스위트도 실행 안 되면 실패** 로 처리한다.

### 테스트를 쓰면서 내 예상이 틀린 것 2개

코드가 아니라 **테스트 기대값**을 고친 사례다. 기록해 둔다.

- `C` 가 한 시간 안에서 "전부 서로 다른 값" 이라 가정했다. 그런데 `phaseRef` 가 항상 구간
  **정중앙**이라 `cos` 대칭으로 앞뒤가 짝을 이룬다. 60칸 → 30개, 40칸 → 20개.
  끝을 잘라 비대칭으로 만들려 해도 `phaseRef` 도 같이 정중앙으로 따라와 불가능했다.
  → "전부 다르다" 대신 **앞쪽 절반 단조 증가 + 1분 차이 두 칸이 다름** 으로 바꿈.
- `ceilTo(30001, SEC30)` 가 `30000` 이라고 기대했는데 `60000` 이었다. **코드가 맞다.**
  30000 경계는 이미 지났으니 그다음이 60000. 내 기대값이 floor 와 ceil 을 헷갈린 것.
- 두 타임라인의 끝 시각이 30초 차이 나는데 S 가 같기를 기대했다. 끝이 다르면 "깨어 있는 꼬리"
  길이가 달라 S 가 0.0007 어긋난다. 코드 문제가 아니라 비교 조건 문제.
