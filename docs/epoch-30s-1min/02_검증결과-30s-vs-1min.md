## 2-1. ★ 이번에 고친 버그 — `clockHours()`

```kotlin
// 버그 (저장소 src/, src-epoch-30s/, src-epoch-1min/ 에 있던 형태)
return local.hour.toDouble()
    + local.minute.toDouble() / 60.0     // ← 이 + 는 새 문장(단항 +)이 된다
    + local.second.toDouble() / 3600.0
```

`return` 뒤에서 줄이 바뀌고 `+` 로 시작하면 Kotlin 은 그 줄을 **새 문장**으로 읽는다.
`return` 은 `hour` 만 돌려주고 분·초는 조용히 버려진다. 컴파일은 통과한다.

 kotlinc 로 두 형태를 직접 돌려 비교한 결과:

| 시각 (KST) | 버그 형태 | 정상 형태 | |
|---|---|---|---|
| 12:24:00 | 12.000000 | 12.400000 | 불일치 |
| 12:24:30 | 12.000000 | 12.408333 | 불일치 |
| 14:47:15 | 14.000000 | 14.787500 | 불일치 |
| 03:24:00 | 3.000000 | 3.400000 | 불일치 |
| 08:41:00 | 8.000000 | 8.683333 | 불일치 |

**불일치 5/5.**

### 영향

`clockHours()`는 `C_sleep` 계산과 `calculatePhaseRef()`(수면 bout 중간 시각의 원형 평균)
양쪽에서 쓰인다. 그래서:

- `C_sleep` 가 **매시간 계단**이 된다. 분 단위 변화가 사라진다.
  한 시각에서 C 오차 최대 **0.009** (진폭 0.15 대비 6%).
- `phaseRef` 도 정시로 뭉개진다. C 전체 위상이 틀어진다.
- **`Process S` 는 영향 없음.** S 재귀는 `dt`(실제 timestamp 차이)와 `isSleep` 만 쓴다.

그래서 초판 문서에서 "현재 S 0.289993 / 1분 0.289342" 는 지금도 그대로이고,
C 계열만 바뀌었다. 소빈이 v3에서 지적해 준 수정이고, 초판에 내가 이 버그를 못 봤다.

### 수정

연산자를 줄 **끝**으로 옮겼다 (통합 v3와 동일). 저장소 3곳(`src/`, `src-epoch-30s/`,
`src-epoch-1min/`)에 반영했고, 부작용 문서를 파일 안에 남겼다.

## 2-2. ★ 이번에 반영한 시각 해석 변경 — KST → UTC

소빈 통합본이 `CsvFileSource.parseTimestamp()` 를 KST 에서 **UTC** 로 바꿨다
(삼성헬스 export 의 `start_time`/`end_time` 이 UTC 라는 근거).

플래그 하나로 분리해 두었으므로 혜지 확인 결과에 따라 되돌릴 수 있다.

```kotlin
private companion object {
    const val SAMSUNG_TIMES_ARE_UTC = true   // ← 아직 소빈의 가설. 혜지 확인 대기.
}
```

**아직 확정되지 않았다.** 이 값을 확정하기 전까지 C 계열 절대 수치를 보고서에 쓰면 안 된다.

### 영향

| 값 | 영향 | 이유 |
|---|---|---|
| `Process S` | **없음** | 수면/각성 순서·지속 시간에만 의존 |
| `sleepRecords` | **없음** | 세션 단위 합계 |
| `C_sleep` | 9시간 밀림 | epoch 시각의 시계 시각을 직접 사용 |
| `phaseRef` | 9시간 밀림 | bout 중간 시각의 원형 평균 |

타임라인 시각 자체도 9시간 밀린다. 초판엔 `2026-09-07 23:41` 로 시작했는데
지금은 `2026-09-08 08:41` 이다. (KST 로 읽으면 18:24 취침 → UTC 로 읽으면 03:24 다음날 취침.)

| 마지막 epoch 시각 | 2026-09-15 08:40:30 | 2026-09-15 08:40:00 | 각자 마지막 칸 시작 (둘 다 08:41:00 까지 덮음) |

### 읽는 법

**epoch 수 = 정확히 절반.** 7일 × 86,400초 ÷ 30초 = 20,160, ÷ 60초 = 10,080. 격자가 의도대로 바뀌었다.

**S 최댓값이 소수점 6자리까지 동일.** 이게 epoch 전환이 안전한 근거다.
`S = S_UPPER − (S_UPPER − S_prev)·e^(−dt/τ)` 형태라 epoch 가 2배가 되어도 물리가 돌아온다.
시각 해석이 UTC 로 바뀌어도 S 는 그대로인 이유도 이것이다.

**C 진폭이 이제 ±0.150000 으로 꽉 찬다.** 초판엔 ±0.149069 였다.
`clockHours()` 가 분·초를 버리고 정수로 뭉개졌기 때문에 진폭의 극값에 못 미치던 것이다.
버그를 고치니 **C 가 설계대로 동작한다.** 이게 2-1절 수정의 직접적인 증거다.

**S 상승 + 하강 = epoch 수 − 1.** 30초: 19,120 + 1,039 = 20,159 ✓ / 1분: 9,559 + 520 = 10,079 ✓
그리고 **평탄 구간 0개.** 매 epoch 에서 S 가 실제로 재계산된다. dt=0 으로 값이 안 바뀌는
epoch 이 없다는 뜻이므로, "1분으로 바꿨더니 절반은 죽었다"는 문제 없다.

**propensity 최솟값이 1분에서 현재값과 같다.** 1분 버전에서 최솟값을 가지는 마지막 epoch 가
타임라인 마지막 epoch 라는 뜻이다. 타임라인 끝이 두 세션 사이에서 잘린 7일 창이라 원래 그런 모양이고,
30초는 마지막 30초 칸이 그 직전보다 S 가 조금 더 내려가서 최솟값이 한 칸 앞선다. 경계 한 칸 차이.

## 2-4. 결과 B — DirectInput 있음 (`applyDirectInput` 하드코딩 검증)

DirectInput 구간: `2026-09-14 02:00:30 ~ 2026-09-14 03:59:30`
(최근 7일 창 안, 두 세션 사이 깨어 있는 구간. 시작을 `:30` 에 두어 epoch 경계와 일부러 어긋나게 했다.)

1분 버전을 **두 가지**로 빌드했다.

- **고정**: `val intervalMs = epochInterval.intervalMs` (내가 고친 코드)
- **되돌림**: `val intervalMs = 30_000L` (4-3절 버그를 일부러 되돌린 것)

| 항목 | 30초 | 1분(고정) | 1분(되돌림) |
|---|---|---|---|
| status | Success | Success | Success |
| epoch 수 | 20,160 | 10,080 | 10,080 |
| 현재 S | 0.278433 | **0.277736** | 0.277852 |
| 현재 propensity | 0.396140 | 0.397238 | 0.397361 |
| S 최솟값 | 0.258868 | 0.257993 | 0.258974 |
| S 최댓값 | 0.999736 | 0.999736 | 0.999736 |

### 읽는 법

**고정 vs 되돌림 결과가 다르다 (0.277736 vs 0.277852).**
→ `applyDirectInput` 안의 `30_000L` 이 결과를 바꾼다는 뜻이고, 고친 코드가 실제로 다르게 동작한다.

**솔직한 범위:** 이 시나리오에서 오차는 `currentS` 기준 0.04% 수준으로 작다.
"크게 틀린다"가 아니라 **"조용히 틀린다"는 이유로 고친 것**이다.
경계에 딱 맞는 시각(22:30 같은 값)을 넣으면 30초·60초 어느 격자에서도 결과가 같아져 차이가 안 드러난다.
사용자가 입력하는 시각이 초 단위로 제멋대로 들어오거나 여러 번 누적될 때 차이가 커진다.

**주의:** 이 시나리오에서 30초에 더 가까운 쪽은 되돌림 빌드였다 (Δ 0.000581 vs 고정 Δ 0.000697).
경계에 가까운 시각을 골라 우연히 상쇄된 결과다. **"고정하면 30초에 더 가까워진다"는 주장을
이 데이터로 할 수 없다.** 고친 근거는 코드 정합성이고, 숫자 근거는 "결과가 실제로 달라진다"까지만 한다.

### ★ 테스트가 버그를 실제로 잡는지 확인했다

회귀 테스트는 통과만 하고 아무것도 안 잡을 수도 있다. 그래서 `clockHours` 버그를
**되돌린 복사본**을 만들어 같은 스위트를 돌렸다 → **6개 FAIL**.
(C 가 시 단위로 뭉개짐 4건, phaseRef 가 정수로 붙음 2건)

### ★ 테스트를 쓰면서 발견한 하네스 버그 2개

1. **`main()` 이 Unit 을 돌려줘서 JVM 종료 코드가 항상 0이었다.**
   `RESULT=FAIL` 이 출력돼도 스크립트는 "전체 통과" 로 집계했다. CI 에 물으면 조용히 통과한다.
   → `exitProcess(code)` 로 수정.
2. **폴더 부재 시 조용히 건너뛰면서 통과로 집계됐다.**
   경로 오타로 아무것도 안 돌았는데 "전체 통과" 가 나오는, 가장 나쁜 오류.
   → `SKIP` 을 별도 상태로 분리 + **아무것도 실행 안 되면 실패** 로 처리.

### ★ 예상이 틀린 테스트 2건 (기록용)

코드가 아니라 기대값을 고친 사례. 나중에 같은 착각 반복하지 않도록 남긴다.

- **C 의 "모두 서로 다른 값" 가정은 불가능하다.** `phaseRef` 가 항상 구간 정중앙이라
  `cos` 대칭으로 앞뒤가 짝을 이룬다. 60칸 → 30개, 40칸 → 20개. 구간을 잘라도 `phaseRef` 가
  따라와서 못 깬다. → **앞쪽 절반 단조 증가 + 1분 차이 두 칸이 다름** 으로 대체.
- **`ceilTo(30001, SEC30)` 는 `60000` 이 맞아.** 30000 경계를 이미 지났으니 그다음이 60000.
  내 기대값이 ceil 을 floor 로 헷갈린 것. 코드는 맞다.

30초와 1분이 같은 물리량을 말하는지 눈으로 대조할 수 있다.

> **주의:** `verify-epoch.ps1` 는 **UTF-8 BOM** 으로 저장돼 있어야 한다.
> PowerShell 5.1 은 BOM 없는 `.ps1` 을 ANSI 로 읽어 한글 문자열이 깨진다.
> 메모장으로 저장할 때는 "UTF-8"이 아니라 **"UTF-8(BOM)"** 을 선택할 것.
>
> 참고: `kotlinc.bat` / `gradlew.bat` 은 .bat라서 이 환경에서 실행이 안 될 수 있다.
> 검증 스크립트는 컴파일러 jar 를 `java -cp` 로 직접 호출해 우회한다.
> 통합 v3 빌드도 같은 이유로 `gradle-gradle-cli-main-*.jar` / `gradle-wrapper.jar` 를
> `java` 로 직접 실행했다.
