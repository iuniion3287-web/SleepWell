## 1. 어떻게 검증했나

두 버전 소스를 각각 jar로 빌드해서 **같은 실제 CSV** 에 돌린 뒤 출력을 비교했다.

```powershell

```

검증 하네스의 `stubs/SharedTypes.kt` 는 앱 전체가 공유하는 타입(`SleepStage`, `SleepSession` 등)을

## 2. 결과 A — DirectInput 없음 (본체 비교)

| 항목 | 30초 | 1분 | 판정 |
|---|---|---|---|
| 실행 결과 | Success | Success | — |
| epoch 수 | 20,160 | 10,080 | **정확히 1/2** |
| futureS 점 수 | 96 | 96 | 동일 |
| 세션 수 | 37 | 37 | 동일 |
| 첫 epoch 시각 | 2026-09-07 23:41:00 | 2026-09-07 23:41:00 | 동일 |
| 마지막 epoch 시각 | 2026-09-14 23:40:30 | 2026-09-14 23:40:00 | 각자 마지막 칸 시작 (둘 다 23:41:00 까지 덮음) |
| **현재 S** | 0.289993 | 0.289342 | Δ 0.000651 (0.22%) |
| **현재 C_sleep** | 0.120753 | 0.122562 | Δ 0.001809 (진폭 0.15 대비 1.2%) |
| **현재 propensity** | 0.410746 | 0.411904 | Δ 0.001158 |
| S 최솟값 | 0.289668 | 0.289342 | |
| **S 최댓값** | 0.999755 | **0.999755** | **완전히 동일** |
| C 최솟값/최댓값 | ∓0.149069 | ∓0.149381 | |
| S 상승 구간 수 | 19,120 | 9,559 | 1/2 |
| S 하강 구간 수 | 1,039 | 520 | 1/2 |
| S 평탄 구간 수 | 0 | 0 | **0이어야 정상** |

### 읽는 법

**epoch 수 = 정확히 절반.** 7일 × 86,400초 ÷ 30초 = 20,160, ÷ 60초 = 10,080. 격자가 의도대로 바뀌었다.

**S 최댓값이 소수점 6자리까지 동일.** 이건 의미가 크다. `S = S_UPPER − (S_UPPER − S_prev) · e^(−dt/τ)`
형태라 각 epoch 에서 `dt` 가 정확히 2배가 되고, 그걸 2번 적용하면 원래 값이 돌아온다.
**epoch 간격이 커졌다고 물리가 달라지지 않음이 숫자로 확인됐다.**

**S 상승 + 하강 = epoch 수 − 1.** 30초: 19,120 + 1,039 = 20,159 ✓ / 1분: 9,559 + 520 = 10,079 ✓
그리고 **평탄 구간 0개.** 매 epoch 에서 S 가 실제로 재계산된다. dt 가 0 이 되어 값이 안 바뀌는
epoch 이 없다는 뜻이므로, "1분으로 바꿨더니 절반은 값이 안 움직인다"는 문제가 없다.

**C_sleep 차이가 상대적으로 조금 크다(1.2%).** 이유:
`phaseRef` 는 수면 bout 중간 시각의 원형 평균이고, bout 경계가 epoch 격자에 snapping 되면서
중간 시각이 조금 어긋난다. 진폭 0.15 안에서 0.0018 차이라 화면·발표 수준에서는 구분되지 않는다.
다만 **C 의 위상이 epoch 간격에 예민하다**는 사실은 알고 있어야 한다. 리듬 위상을 논문 값으로
쓸 계획이면 epoch 을 고정하고 그 기준으로 보고서를 쓰는 게 맞다.

**propensity 최솟값이 30초에서 0.410421, 1분에서 0.411904.** 두 번째 값이 현재 propensity 와 같다.
1분 버전에서 최솟값을 가지는 마지막 epoch 가 타임라인 마지막 epoch 라는 뜻이고, 타임라인 끝이
두 세션(09-13 18:24~23:10, 09-14 19:11~23:41) 사이에서 잘린 7일 창이라 원래 그런 모양이다.
30초 버전에서 최솟값이 마지막보다 약간 앞선 건 마지막 30초 칸이 그 직전보다 S 가 조금 더 내려간
것뿐이다. **버그가 아니라 경계 한 칸 차이다.**

## 3. 결과 B — DirectInput 있음 (`applyDirectInput` 하드코딩 검증)

DirectInput 구간: `2026-09-14 02:00:30 ~ 2026-09-14 03:59:30`
(최근 7일 창 안, 두 세션 사이 깨어 있는 구간. 시작을 `:30` 에 두어 epoch 경계와 일부러 어긋나게 했다.)

여기서 1분 버전을 **두 가지**로 빌드했다.

- **고정**: `val intervalMs = epochInterval.intervalMs` (이번에 고친 코드)
- **되돌림**: `val intervalMs = 30_000L` (4-3절에서 지적한 버그를 일부러 되돌린 것)

| 항목 | 30초 | 1분(고정) | 1분(되돌림) |
|---|---|---|---|
| status | Success | Success | Success |
| epoch 수 | 20,160 | 10,080 | 10,080 |
| 현재 S | 0.254868 | **0.253984** | 0.254206 |
| 현재 propensity | 0.379134 | 0.380385 | 0.380691 |
| S 최솟값 | 0.254527 | 0.253984 | 0.254206 |

### 읽는 법

**되돌림 빌드와 고정 빌드의 결과가 다르다(0.253984 vs 0.254206, Δ 0.000222).**
→ `applyDirectInput` 안의 `30_000L` 이 실제로 결과를 바꾼다. 고친 코드가 실제로 다른 결과를 낸다는 뜻이다.

이 시나리오에서 다루는 구간이 epoch 경계와 어긋나도록 골라서, 되돌린 쪽이
직접 입력 구간을 1분 epoch 기준으로 절반 크기(`ts` + 30초)로만 처리하게 된다.
그래서 낮잠으로 반영되는 시간이 어긋나고 S 곡선이 조금 달라진다.

**솔직한 범위 한계:** 이 테스트에서 오차 크기는 `currentS` 기준 0.09% 수준으로 작다.
버그가 크지 않다는 뜻이 아니라, **경계에 딱 맞게 입력한 시간(22:30 같은 값)에서는
30초·60초 어느 격자에서도 결과가 같아져 차이가 안 드러난다**는 뜻이다.
사용자가 입력하는 시각이 초 단위로 제멋대로 들어올 때, 또는 여러 번 입력받아 누적될 때
차이가 커진다. 그래서 "크게 틀린다"고 할 수는 없고, **"조용히 틀린다"는 이유로 고친 것**이다.

**한 가지 주의:** 이 시나리오에서 30초 결과와 더 가까운 쪽은意外하게 *되돌림* 빌드였다
(0.254206 vs 0.254868 → Δ 0.000662 / 고정 0.253984 → Δ 0.000884).
경계에 가까운 시각을 골라서 되돌린 쪽의 오프셋이 우연히 상쇄된 결과다.
"고정하면 30초에 더 가까워진다" 같은 주장은 이 데이터로 할 수 없다.
고친 근거는 **코드 정합성**이고, 숫자 근거는 "결과가 실제로 달라진다"까지만 한다.

## 5. 하지 못한 것 (한계)

| 항목 | 상태 |
|---|---|
| Android Gradle 빌드 | **안 함.** 이 폴더에는 앱 프로젝트(`build.gradle.kts`, `HealthModels.kt`)가 없어서 Gradle 빌드가 불가능하다. kotlinc 개별 컴파일만 했다. 앱에 붙일 때는 소빈이 Gradle 빌드로 한 번 더 확인해야 한다. |
| 단위 테스트 | **없다.** 원래도 테스트가 없는 상태라, 30초 버전을 그대로 두고 회귀만 비교했다. |
| `MainActivity` / `SleepStageChart` / `Exporters` | 소빈 파일이라 안 봄. `AnalysisResult` 에 필드가 늘었으므로 여기서 컴파일 문제가 없는지 확인이 필요하다(기본값이 있어大概率 문제없음). |
| 1분 vs 30초 정확도 비교 | **할 수 없었다.** 두 버전을 Sleep-EDF 정답과 비교하려면 1분 → 30초 역집계 규칙이 먼저 정해져야 한다. 소빈 #2 파이프라인 작업과 겹친다. |

## 6. 재현 방법

```powershell
# 자동 탐색되는 CSV 로 실행
powershell -ExecutionPolicy Bypass -File tools\verify\verify-epoch.ps1

# CSV 직접 지정
powershell -ExecutionPolicy Bypass -File tools\verify\verify-epoch.ps1 `
    -Csv "C:\path\to\sleep_stage_cleaned.csv"

# kotlinc 를 못 찾으면
powershell -ExecutionPolicy Bypass -File tools\verify\verify-epoch.ps1 `
    -Kotlinc "C:\Program Files\Android\Android Studio\plugins\Kotlin\kotlinc\bin\kotlinc.bat"
```

산출물(`tools/verify/out/`):

| 파일 | 내용 |
|---|---|
| `result-30s.txt` / `result-1min.txt` | DirectInput 없는 본체 결과 |
| `result-30s-di.txt` / `result-1min-di.txt` | DirectInput 있는 결과 |
| `result-1min-buggy-di.txt` | 되돌린(버그 있는) 1분 빌드 결과 |
| `verify-*.jar` | 빌드 산출물 (커밋 대상 아님) |

각 결과 파일에는 15분 간격 그래프 샘플이 들어 있다. 시각 좌표가 붙어 있어서
30초와 1분이 같은 물리량을 말하는지 눈으로 대조할 수 있다.

> **주의:** `verify-epoch.ps1` 는 **UTF-8 BOM** 으로 저장돼 있어야 한다.
> PowerShell 5.1 은 BOM 없는 `.ps1` 을 ANSI 로 읽어 한글 문자열이 깨진다.
> 메모장으로 저장할 때는 "UTF-8"이 아니라 **"UTF-8(BOM)"** 을 선택할 것.
